# v1.0 门禁清单

从 0.x 升到 1.0 意味着把「可变的接口」变成「承诺不破坏的接口」。下面每一项
都有可验证的判据；未全部达成前保持 0.x。

## 1. 配置 schema

- 判据：连续两个 0.x 发布之间，`version = "v1alpha1"` 的配置文件不改一行即可
  同时用于 `create`、`add`、`upgrade`（回归测试：`kurin-config` 中固定若干
  历史配置样本做 parse 断言）。
- 晋升 `v1` 的条件：至少 90 天、跨越 3 个发布版本无破坏性变更。
- 晋升后规则：删除字段或改变语义 = 主版本变更；新增字段必须 `#[serde(default)]`
  或 `Option<T>`；未知字段目前是硬错误（`deny_unknown_fields`），1.0 起对
  `v1` 配置保留该行为，因此新增字段前必须先有默认值。

## 2. `--json` 事件流

- 已冻结的事件类型：`task-start` / `task-done` / `task-failed` /
  `skip`（如有）/ `stage-done` / `cluster-ready`。
- 判据：`e2e/tier1/assert.sh` 之外增加一个契约测试，断言每种事件的字段集合；
  字段删除或改名为破坏性变更。新增可选字段不算。
- 事件仅供机器读取（进度展示、CI 判定），不承诺语义顺序之外的时序。

## 3. 升级与证书

- 已用 tier-2 e2e 验证：`upgrade` 单次 N → N+1（kubeadm，含离线
  `--offline`）、`certs rotate`、`status` 探测。
- 1.0 承诺：N → N+1 直接升级；跨多个小版本需逐级（文档写明，不做魔法）。
- k3s 的升级/证书路径目前只覆盖安装与 HA，不含升级——1.0 前要么补齐 tier-2，
  要么在文档中把 k3s 标为「安装完整、升级不承诺」。

## 4. 可诊断性

- `kurin status` 对每类失败（节点 NotReady、etcd 成员缺失、证书将过期、
  LB 后端全挂）给出可执行的下一步，而不是原始 JSON 堆。
- 判据：`docs/troubleshooting.md` 每一条都有对应 jsonevent/status 输出样本。

## 5. 不做的事（写死在文档里）

- 不做 KubeSphere；不做通用插件系统/playbook 语言；不做 Docker 运行时；
  不做半状态事务回滚（失败后靠 `kurin delete` + 重建，文档明确说明）。
- 这些是设计边界，不是「1.0 之后再说」。

## 6. 发布工程

- `just release <ver>` 一次完成双架构 musl 构建、tag、CHANGELOG 段落提取、
  四资产上传；`CHANGELOG.md` 保持 Keep a Changelog 结构。
- 判据：连续两个发布用该流程时间 < 10 分钟且无需手工补救。
